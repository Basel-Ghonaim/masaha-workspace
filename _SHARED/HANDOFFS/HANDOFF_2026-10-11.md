## 3. The method (since M1 and M2, 2026-10-08)

**One Work Item, seven phases** (workflow §2): (1) **analysis with you and the owner** — scope, open
decisions with options and a recommendation, settled decisions now doubtful, related findings; the
owner decides; (2) **the prompt** — short, in the template below; (3) the worker **plans** in plan
mode (`write-plan`), with a *Stronger decisions* section and, for a screen, *Design issues*; it
**saves the plan** to `PLAN\<ITEM>_PLAN.md` and **stops**; (4) you review the plan and write a reply
(`PROMPT\<ITEM>_PLAN_REPLY.md`) — the owner pastes it; (5) the worker builds, every new test seen
failing first, then **every lane locally once on the head**, build + `check:build`, a real run
(a change with no code: `format:check` + `check:links` only); (6) PR, CI green and `CLEAN`, the
report saved to `REPORT\<ITEM>_REPORT.md` (`final-report`, with `git merge-tree` against the other
open PRs); (7) **review**: a separate review conversation when the PR touches more than ~25 files,
authorization/security, a transaction, the schema, adds a dependency or changes CI / the build
checks; otherwise you review it.

**The prompt template:** header (worker, folder, branch cut command, databases/ports, size cap, the
PLAN and REPORT paths, "follow the skills"); §1 the task in brief; §2 read first (the capability
document first; name only what the item needs — the owner insists the worker reads nothing useless);
§3 the settled decisions (D1, D2 …, "review them in *Stronger decisions*"); §4 findings folded /
numbering range; §5 risks; §6 boundaries with the other workers; §7 checks (**only the lanes the
change can touch** — the owner insists), PR (title ≤ 50, labels), the documents to update.

**Reviews of PRs.** For big PRs the owner now uses **free tools in parallel** (Copilot, OpenCode,
Codex) with one shared review prompt (each writes `REVIEW<n>_<TOOL>_REPORT.md`). You then **merge the
reports into one** (`REVIEW<n>_MERGED_REPORT.md`, duplicates merged, each finding naming its
reviewers), **verify each finding against the code with read-only subagents** (two, in parallel,
split by area), and write **one fixes list** (`PROMPT\<ITEM>_FIXES.md`). On PR #57: Copilot and
Codex found the two real bugs; OpenCode found four documentation/rule items the others missed.

**Fixes rounds:** fold into their commits (fixup + autosquash, `--force-with-lease`); ONE "Review
fixes" comment; a "Review fixes" section added to the report.

**Conflicts:** check `git merge-tree --write-tree` between open PRs at every report; decide the merge
order early; the second branch rebases in its last push. A conflict only in documents takes the
**fast path** (keep both sides, `format:check` + `check:links`, one push).

**After a merge:** delete the remote branch; main folder `git pull --ff-only` (or
`git fetch origin main:main` if A is mid-item); move `masaha-b` (and any task worktree) with
`git switch --detach origin/main`; if the schema changed, `npx prisma generate` and apply the
migration to `masaha_b_dev` (read `DATABASE_URL` from `masaha-b\apps\api\.env` without printing it,
`migrate status` → `migrate deploy` → status); if `packages/shared` changed, rebuild its `dist` in
each folder (a stale `dist` once hid a CI failure); `npm ci` only if dependencies changed.

**Models (the owner economises tokens):** Opus 5.5 at effort **high** for judgment (design reviews,
the design fixer, code review gates); Sonnet for mechanical items (small docs, M4). Non-Claude tools
**only as read-only reviewers** — a non-Claude worker that built the README produced low quality.
