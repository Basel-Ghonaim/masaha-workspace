## 4. The owner's standing rules

- **Quality over speed.** Defence by **16 January 2027**. The owner decides architecture and scope;
  every decision is presented with options and a recommendation. Take the stronger decision even over
  our own docs; the code governs what is built (documents follow it).
- **No production code only for tests** (no parameter, option or callback only tests pass; a service
  creates its own repository; tests stub the platform's seams; no `vi.mock` of a module).
- **One responsibility per file**; files grouped by operation in `hooks/` and `components/`.
- **One home per fact** in the documents; capability documents own capability decisions; platform
  documents own mechanisms; records (plans, findings, ADRs) are not rewritten.
- **Feature documents:** a capability gets `docs/features/<backend-module>.md` in the PR where it first
  reaches a stable core (first merged, reviewed slice); every later PR that changes it updates it. A
  capability not yet stable has none and is worked as before. Length is judged by coherence, not the
  ~1,200-word guide.
- **Superpowers, selectively** (workflow §10): TDD with `writing-good-tests.md`, systematic debugging,
  verification before completion, receiving code review (adapted), parts of writing-plans; not the
  rest. Enabled only in each folder's untracked `.claude/settings.local.json`
  (`superpowers@claude-plugins-official`).
- **Commit subjects ≤ 50 characters.** No tool attribution anywhere. Report only once CI is green.
- **Token economy matters:** caps stated in every prompt (the owner lifted the cap only for the large
  documentation effort).
